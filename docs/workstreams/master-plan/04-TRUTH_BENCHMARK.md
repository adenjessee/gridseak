# 04 — TRUTH BENCHMARK: own the category's measuring stick

Status: DRAFT v1 (2026-07-01)
Depends on: 02 (Rust + TS compiler tier, to be winnable), 03 (public
repo, to be citable). Exit = Gate G3. Feeds plans 05–08.
Executor profile: agent with Rust + scripting; labeling needs care, not
special skill.

## Context and strategic intent

No public, reproducible accuracy benchmark exists for the "code graph /
structural context for AI agents" category (verified by market research
2026-07-01). Competitors won attention with unaudited claims (CodeGraph:
"70% fewer tool calls"). GridSeak is the only tool in the category whose
edges carry confidence at all — so a benchmark that scores **calibration**
("when a tool says High, how often is it right?") reframes the category
around the axis where GridSeak stands alone. The benchmark must be honest
to the point of discomfort: publish where GridSeak loses. Credibility is
the product being manufactured here; a rigged benchmark is worse than none.

## Deliverable

A standalone public repo `gridseak-truth-benchmark` (plus a results page)
where `git clone && make bench` reproduces every number. Contents:

1. **Corpus**: 5 pinned-commit OSS repos people recognize; start:
   - TypeScript: `zod` (known measured gap → honest redemption arc),
     one mid-size app-style repo (e.g. `excalidraw` subset).
   - Python: `fastapi` or `httpx`.
   - Rust: `ripgrep`.
   - Polyglot stretch: one monorepo slice.
2. **Ground truth**: labeled call-edge samples per repo:
   - Sample ~300 call sites per repo, stratified: same-file calls,
     cross-file, cross-module, method-on-object, dynamic-ish cases.
   - For each: the true callee (file, symbol) or "external/stdlib" or
     "statically undecidable" — labeled via language-native oracles
     (TS: tsserver `definition` at the site; Rust: rust-analyzer;
     Python: pyright) then **human-spot-checked 10% per repo**; disagreements
     resolved by reading the code. Labels stored as JSON with a schema +
     provenance note per label (oracle vs human).
   - Undecidable cases stay in the set — tools should NOT claim them.
3. **Systems under test** (adapters that normalize each tool's output to
   `(caller, callee, confidence?)`):
   - GridSeak (`gridseak scan`, read SQLite graph).
   - CodeGraph (its SQLite/CLI output).
   - Serena (LSP-live; drive `find_referencing_symbols`-style queries).
   - Grep-baseline (ripgrep name-match, the null hypothesis).
   - Optional: tree-sitter-only GridSeak mode (ablation: how much the
     compiler tier adds — this is the marketing number for plan 07).
4. **Metrics**:
   - Precision / recall / F1 on labeled edges, per repo and pooled.
   - **Calibration**: for each confidence bucket a tool emits, observed
     precision; expected-calibration-error (ECE). Tools without
     confidence get one bucket — the point being made visible.
   - **Honesty rate**: fraction of statically-undecidable sites where the
     tool either abstains or labels low-confidence (vs confidently wrong).
   - **Token/efficiency proxy**: for 20 scripted agent tasks ("what
     breaks if I change f?"), tool-call count + bytes returned to reach
     the correct answer, vs the grep baseline. Scripted, not vibes:
     a driver executes fixed query plans per tool.
   - Wall-clock scan/index time per repo (feeds plan 05 budgeting).
5. **Outputs**: `results/*.json` (machine-readable, schema-versioned),
   a generated `RESULTS.md` with tables, and per-repo detail pages.
   Everything regenerated by `make bench`; CI re-runs a small slice
   weekly to catch drift.

## Steps

1. Scaffold repo: corpus manifest (git URLs + pinned SHAs), Makefile,
   `harness/` (Rust or Python — choose Python for contributor
   accessibility), adapters as one module per tool with a common trait.
2. Build the labeling pipeline (oracle drivers + sampling + human-review
   queue file). Deliver labels for TS first (aligns with plan 02 Phase C
   landing), then Rust, then Python.
3. Implement adapters; verify each tool runs pinned versions from a
   lockfile (`tools.lock` with versions + install commands).
4. Run, generate RESULTS.md, sanity-review every surprising number by
   hand before publishing (a too-good number is a bug until proven).
5. Publish; submit to the third-party comparison-page authors found in
   research (the rywalker research pages, zzet.org comparison, dev.to
   reviewers) — a short factual note: "reproducible benchmark, here's
   where our tool loses" is the most credible cold outreach that exists.
6. Wire the headline numbers back into the main README and the MCP
   `tier_legend` vocabulary release (add compiler tier wording here).

## Acceptance criteria (binding — Gate G3)

- [ ] `git clone && make bench` reproduces all published numbers on a
      clean machine (document required toolchain versions).
- [ ] >= 3 languages, >= 4 systems under test, >= 900 labeled sites total,
      10% human-verified with recorded adjudications.
- [ ] GridSeak ECE <= 0.10 on pooled results (else: fix the engine or the
      claim, do not ship the benchmark with a broken headline).
- [ ] Published results include at least one axis where GridSeak loses,
      stated plainly in RESULTS.md.
- [ ] Weekly CI slice green.

## Risks and honesty rules

- Adapter fairness: each competitor adapter must be reviewed against that
  tool's docs so we don't strawman it; document each adapter's known
  limitations in-repo. Invite competitors to PR fixes to their adapters
  — that invitation itself is distribution.
- Label leakage: oracles overlap with GridSeak's own tiers (rust-analyzer,
  pyright). Mitigate: human spot-check is stratified toward cases where
  oracle == GridSeak backend; document the overlap prominently.
- Do not name the benchmark after GridSeak's weaknesses or strengths;
  neutral name, neutral tone, let numbers speak.
